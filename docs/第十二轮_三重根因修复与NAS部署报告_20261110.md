## 三、排查方法

### 3.1 先证明数据链路无罪

用户怀疑「数据没到最新」。实测反驳：

**结论：数据接收链路无问题，问题在判定与执行逻辑。**

### 3.2 用「体量矛盾」定位

| 观察 | 推理 |
|---|---|
| 池子 200 只，每天报 196–200 个信号 | 几乎 100% 命中 → 不可能都是当日机会 |

| 抽查 15 只：当日真信号 **0**，旧信号 14 | 确认是历史信号堆积 |

### 3.3 精确复现（决定性证据）

针对日报中一条真实拦截记录（`605178.SH`：止损价 90.62 vs 买入价 64.15）：

| 项目 | 复现值 | 日报值 | 匹配 |

## 四、三重根因详解

### 4.1 P0-B：因子方向写反了（最致命）

#### 因子本意

`src/lihu_quantify/strategy/intraday_reversal.py` 模块 docstring：

> 因子值 = `-Σ ln(close/open)`（近20日累计日内收益取负 → 日内跌得越多越超卖看多）

即：**日内跌得越多 → ir20 越大 → 越超卖 → 越看多**，应买**高分位**。

#### 实际实现（修复前）

```python
mask = d["ir20_pct"].notna() & (d["ir20_pct"] <= self.entry_pct)   # entry_pct=0.20
```

买的是**最低 20% 分位** —— 与因子定义**正好相反**。

#### 独立验证 1：截面 IC

37 只股票 / 11,052 个观测（2025-01 ~ 2026-11）：

| 指标 | 数值 |
|---|---|
| Spearman(ir20_pct, 未来20日收益) | **+0.0808**（p=1.79e-17） |
| 门禁3 记录 RankIC | +0.0804 |

**两者几乎完全一致 → 因子本身没问题，是实现把它用反了。**

五分组单调性：

| 分位 | 样本 | 未来 20 日平均收益 |
|---|---|---|
| **Q1（最低，代码实际买的）** | 2211 | **−0.18%** |
| Q2 | 2210 | +0.38% |
| Q3 | 2210 | +1.21% |
| Q4 | 2214 | +0.89% |

### 4.2 P0-A：僵尸信号（每日扫描路径漏修）

#### 根因

`src/lihu_quantify/strategy/base.py` 修复前：

```python
def latest_signal(self, df: pd.DataFrame) -> Signal | None:
    """取最新一根 bar 的信号（每日扫描用）"""
    signals = self.scan(df)
    return signals[-1] if signals else None    # ← 返回"最后一根合格 bar"，不是"最新 bar"
```

`signals[-1]` 取的是「窗口内最后一根**满足条件**的 K 线」，而不是「今天这根」。
对带 10 交易日限频的 `IntradayReversal`，该信号可能滞后数十个交易日。

而调度器随后用 `df.iloc[-1]["close"]`（**今日**收盘价）执行 ——
**旧止损价配今日执行价**，必然触发「铁律1：止损价不低于买入价」。

值得强调的是：`on_bar()`（事件驱动路径）**早就修过同一个问题**，注释写着
「修复5b：当日 bar 无信号必须返回 None，删除 signals[-1] 兜底」。
**同一个坑，回测路径修了，实盘扫描路径漏了。**

#### 证据 1：单只精确复现（见 3.3，滞后 65 个交易日）

#### 证据 2：7 笔真实买入，无一例外

   （`stale_dropped` / `stale_sample` 写入 summary）。
3. **可观测性**：日报显式标注「另有 N 只历史信号因非当日已丢弃」，
   不静默吞掉 —— 避免再次出现「有 199 个信号却不买入」的误解。

### 4.3 P1：市场闸门滞后

#### 根因

`src/lihu_quantify/market.py` 原实现只用 **20 日累计涨跌幅**三分段：

| 原判据 | 状态 |
|---|---|
| ≥ +3% | 上涨 |
| ≤ −3% | 下跌 |
| 其余 | 震荡 |

问题：趋势反转初期，前几天大涨，但 20 日累计仍被前期下跌拖累未达 +3% → 持续判「震荡/下跌」
→ `block` 模式持续关门。实测**连续 24 个交易日判「下跌」**（2026-10-08 起）。

#### 修复（不动阈值与窗口，只加正交维度）

| 场景 | 新判据 | 结果 |
|---|---|---|
| 20 日涨幅 ≥ +3% | 主维度 | 上涨 |
| 20 日涨幅 ≤ −3% | 深跌保护：近 5 日 ≥ +5% 才翻多 | 强反弹 / 下跌 |
| 20 日涨幅 ∈ (−3%, +3%) | MA5 > MA20 且 MA5 上行，**或** 近 5 日 ≥ +2% | **上涨** |
| 震荡区无动量 | — | 震荡 |

保留原阈值/窗口（尊重 `settings.yaml` 中「不调参」的既有决策），仅增加短期动量这一正交维度；
深跌段要求更强的反转确认（+5%），避免下跌中继的假反弹骗开仓。

- **提交**：`7346d29`

## 五、闸门严格度 A/B（修复后重新验证）

P1 的宽松化是在「因子方向错误」的背景下调优的。方向翻正后策略变成**真正的逆势反转**，
理论上与「只在上涨段开仓」的 block 闸门存在张力，因此必须重测。

148 只 / 2025-01-01 ~ 2026-11-10 / 含成本：

| 闸门 | 总收益 | 年化 | 夏普 | 最大回撤 | **卡玛** | 胜率 | 盈亏比 | 轮次 |
|---|---|---|---|---|---|---|---|---|
| S 原版严格 | **+15.31%** | 8.34% | **0.57** | −15.14% | 0.55 | 40.1% | 2.24 | 177 |
| **L 宽松（当前）** | +13.39% | 7.32% | 0.41 | **−8.64%** | **0.85** | 40.9% | 1.87 | 264 |
| N 无闸门 | +1.18% | 0.66% | −0.11 | −12.54% | 0.05 | 40.6% | 1.49 | 323 |

### 结论

1. **闸门存在本身被强验证**：有闸门 +13.4%~+15.3%，无闸门只有 +1.18%。
   且闸门的作用**取决于策略方向**——方向错时闸门是负贡献（−7.25pp），方向对时是正贡献（+12.21pp）。
2. 严格版收益与夏普略高，但**回撤是宽松版的 1.75 倍**；**卡玛 0.85 vs 0.55，宽松版更优**。
3. **决策（用户 2026-11-10 拍板）：保留宽松版闸门 + `block` 模式**，取向为控回撤。

### 6.2 首次部署事故：duckdb SIGILL（生产中断约 5 分钟）

| 环节 | 情况 |
|---|---|
| 现象 | `lihu-scheduler` / `lihu-web` 双双 `Restarting (132)`；132 = **SIGILL**；容器日志为空 |
| 定位 | 逐包 `import` 对照：新镜像 `import duckdb` → `Illegal instruction (core dumped)`，其余包均正常 |
| **根因** | Dockerfile 用 `pip install -r`，依赖全是 `>=` 下限且**无锁定文件**，每次 rebuild 都拉最新版 → duckdb 由 1.5.5 升到 **2.0.0**，其预编译二进制使用 **AVX** 指令；NAS CPU 为 **Intel Celeron J1900，仅支持 SSE4.2、无 AVX** |
| 处置 | 取证 → `docker tag aade8f267fd5 latest` → `--no-build` 拉起 → 恢复 |
| 修复 | 新增 `constraints.txt`（由可用旧镜像 `pip freeze` 导出的 **44 包精确锁定**）；Dockerfile 改 `pip install -c constraints.txt`；`pyproject` 给 duckdb 加上界 `<2.0.0` |

### 6.3 后续两次挫折（均已修复）

| 次序 | 问题 | 修复 |
|---|---|---|
| 第二次 | 实际部署成功，但 `latest_signal` 探针报 OLD 触发误回滚。原因：探针判据是「源码不含 `signals[-1]`」，而新实现 docstring 恰好描述了旧行为 | 改判唯一属于新实现的 `_same_date(s.trade_date, last_date)` |
| 第三次 | `docker exec ... --run-now --force` 失败：DuckDB 单写锁被常驻进程（PID 1）持有 | 补跑改为「stop 常驻 → `run --rm -T ... timeout 420` → up -d → wait_healthy」 |

`run_scheduler.py --run-now` 跑完不退出而进入调度等待态，故需 `timeout` 兜底
（退出码 124 属预期，不是失败）。

### 6.4 部署脚本的加固（本次事故本可自动兜住）

- `wait_healthy()`：重建后轮询容器健康，`Restarting` 视为硬失败
- `current_image_id()`：部署前记录旧镜像 ID
- **失败自动回滚**：重建/健康检查/verify 任一失败 → retag 旧镜像 + `--no-build` 重启
- verify 增加「依赖可 import（duckdb 等原生库）」探针，原生库崩溃不再被当作"输出为空"

### 9.3 NAS 固定 IP

DHCP 已致地址漂移两次，每次都会让同步脚本静默失效（曾导致 9/29、10/7 被误判为「NAS 离线」）。

**做法**：不手改 `ifcfg`（会与 DSM 内部状态不同步、易丢 DNS），改走 DSM Web API
`SYNO.Core.Network.Ethernet`（图形界面背后的同一接口），由 DSM 统一接管网关与 DNS。

三步可停流程：
1. **no-op 校验**：用当前值发一次 `set`，只验字段结构，不改配置
2. **切静态**：仅翻转 `use_dhcp → false`，IP/掩码/网关/MTU/VLAN 全部沿用现值（IP 不变）
3. **验证 + 失败自动回退**：校验 DSM 记录、内核地址、网关、主机 DNS、**容器内解析 Tushare**、容器健康

**结果**：`use_dhcp=false`、`IPADDR=192.168.123.204`、网关 `192.168.123.1`、
DNS `223.5.5.5 / 114.114.114.114` 全部保留；`dhclient@eth0` 已停止；
主机与容器内均能解析 `api.tushare.pro`；看板 8000 / DSM 5000 均 200。
配置已落盘 `ifcfg-eth0`（`BOOTPROTO=static`），重启后仍生效。

工具：`scripts/_nas_set_static_ip.py`（`--revert` 可一键回退 DHCP）。

> **仍需人工完成**：设备侧静态 IP 只是"自己声明"，路由器不知道 `.204` 已被占用。
> 建议在路由器 DHCP 池中**排除 `192.168.123.204`**（或按 MAC `00:11:32:7b:55:93` 做静态绑定）。

### 9.4 NAS → 本机数据导入（供迭代）

新增 `scripts/import_from_nas.py`，方向严格单向（NAS → 本机）；本机 `data/` 从不反向推送。

- 默认导入约 **0.5MB 压缩包 / 319 文件**：账本（主+4影子）、止损登记、`last_scan`、
  `filter_stats`、`heatmap_snapshot`、`strat_pool_*`、`swing_pool`、167 份报告、`outputs/*.json`
- 可选：`--with-db`（duckdb+wal）、`--with-logs`

- 安全：覆盖前打包备份、JSON 全量校验、只覆盖同名文件、写 `data/_IMPORTED_FROM_NAS.json` 标记

**实测：导入后本机看板与 NAS 逐项一致（10 项指标全 OK）。**

## 十二、经验教训

### 12.1 三个 bug 的共同模式

> **「同一个坑，一条路径修了，另一条路径漏了」**

| 位置 | 已修路径 | 漏掉的路径 |
|---|---|---|
| 信号新鲜度 | `on_bar()`（回测/事件驱动，修复5b） | `latest_signal()`（每日扫描） |
| 市场状态判定 | `market.py`（巡检） | `web/server.py`（看板） |
| 策略构造 | `_scan_impl`（巡检） | `collect_signals`（run_live） |

**改进方向**：凡"两份实现做同一件事"，应收敛为单一实现（本次已把策略构造收敛；
信号新鲜度改为基类唯一实现 + 调度器双保险；看板改为复用 `classify_market_state`）。

### 12.2 可观测性的价值

本次能快速定位，靠的是**让异常显形**：

- 「每天 199 个信号」这个数字本身就是异常信号（一个 200 只的池子不可能几乎全命中）
- 11/03–11/10 日报**字节数完全相同**，暴露内容静态
- 修复后新增 `stale_dropped` 计数并要求日报显式标注，**不静默丢弃**

### 12.3 生产部署的教训

- **依赖必须锁定**：`>=` 下限 + 无 lockfile = 每次 rebuild 都是俄罗斯轮盘。本次为此付出 5 分钟生产中断。
- **老硬件是隐性约束**：Celeron J1900 无 AVX，新版本二进制会直接 SIGILL，且**容器日志为空**，极难联想。
- **"命令没报错"不等于成功**：必须进镜像内验证逻辑真的存在（`inspect.getsource` 探测）。
- **先备份再覆盖**：本次 4 个回滚点全部由脚本自动生成，事故时才有底气。
