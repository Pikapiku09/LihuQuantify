## 一、两个真实翻车案例

这两次错误都不是"能力不足"，而是**没有制度化约束**——知道结果之后再做选择，
任何人的判断力都会失真。留档的目的不是自责，而是让同类错误在流程上不可能重演。

### 案例 1：未来函数 `lag=0`，虚增 52.49pp

**错在哪**：闸门的市场状态（`ret_20d` / `ret_5d` / `MA5`）是用**当日收盘价**算出来的，
回测却把**当日 close-to-close 涨幅**也算进策略收益——用当天收盘后才得到的信号，
去赚当天的涨幅。这就是前视偏差（未来函数）。

**实测**（详见 [决策日志](决策日志.md) §3）：

| 口径 | 新宽松闸门 | 旧严格闸门 | 买入持有 |
|---|---|---|---|
| 含伪交易日、`lag=0`（历史记录） | **+71.63%** | +34.11% | +9.31% |
| 剔除伪交易日、`lag=0` | **+61.87%** | — | — |
| 剔除伪交易日、**`lag=1`（T+1 诚实口径）** | **+9.38%** | **+7.24%** | **+12.30%** |

同一个未来函数把 9.38% 吹成 61.87%，**虚增 52.49pp**。由此推得的"超额 +62.3pp"
"滚动胜率 94%""当前配置落在有效区间中部"**全部作废**。

**教训**：任何回测数字，先问"信号用的是哪一天的数据、收益从哪一天起算"。
没有标 `lag` 的收益数字，默认当它不可用。

### 案例 2：知道 MACD 结果之后才挑规则

**错在哪**：在若干离场规则（MACD 死叉 / KDJ 死叉 / K 线见顶 / 固定持有……）里
挑出「MACD 死叉离场 +27,072 元」，是在**已经看过结果之后**挑的。这不是假设检验，
是多选项里挑最大值——样本外几乎必然衰减（"赢家诅咒"）。

**已知数字**：435 轮回测，MACD-only 离场收益 **+2.41%** vs 现行 MA10 破位 **+0.72%**。
> 【来源】Lead 2026-11-14 分析，尚未归档成报告，数字待复核；
> 本案例的价值在流程，不在这个 +27,072 本身。

**教训**：规则必须在看结果之前登记，并写死样本切分与通过标准。
登记之后即使"再发现一个更好的规则"，也只能作为**新假设**另立条目，不能替换原假设。

## 二、三条规则

### 规则 1：预注册（先写假设，后做验证）

任何要上线的策略/参数变更，必须先进入登记册，写清四件事：

1. **rationale**：为什么"先验地"相信它（不是看到了什么结果）；
2. **method.universe**：样本范围（哪个账本、多少轮、什么过滤）；
3. **窗口**：`is_window`（定参）与 `oos_window`（验证）；
4. **pass_criteria**：通过标准（如"OOS 改善 ≥2.0pp、MDD 增加 ≤5.0pp、是否需要显著"）。

登记册 schema 是**封闭集合**（未知字段直接报错），避免拼写错误被静默忽略。

### 规则 2：样本外（IS 定参，OOS 验证，不得重叠）

- IS 窗口只用于选参数/选规则；OOS 窗口只用于验证，**不参与任何选择**；
- `is_window` 结束日必须早于 `oos_window` 开始日，**边界日也不得复用**；
- 判定只看 OOS：本模块规定 `compare_oos` 以"OOS 相对 IS 的改善（百分点）"
  是否达到预注册门槛为准；
- 样本外不达标 → 假设记为 `failed`，**不得**回头改 OOS 窗口重试。

工具：`src/lihu_quantify/backtest/split.py`
（`parse_window` / `assert_no_overlap` / `split_by_date` / `compare_oos`，全部纯函数）。

### 规则 3：口径声明（FIFO 逐笔 vs 波口径，必须写明）

同一批成交，两种配对口径给出的结论可能相反：

| 口径 | 定义 | 适用判断 | 已知偏误 |
|---|---|---|---|
| `fifo` | 逐笔先进先出配对（`_pair_rounds`） | 可与模拟盘逐轮对比、算胜率/EV | 会把一波完整操作切成很多小笔，**低估长期持有效果** |
| `wave` | 从 0 仓建仓到完全清仓算"一波" | 回答"这一波我赚了多少" | 不同波之间仓位/持有期不同，**不可直接比收益** |

登记册 `method.pairing` 必填且只允许 `fifo | wave`；任何报告引用收益数字都必须写明
用的是哪一种口径。实证例子（[交接摘要](交接摘要_20261114.md) U5）：真实交割单里
分批止盈 73 波 **+22,593**（61.6%）vs 一次性清仓 41 波 **−19,728**（39.0%），
但分批波仓位大 **3.1 倍**、持有久 **2.9 倍**——不声明口径、不做中性化就比较，
结论就是假的。

## 三、登记册 schema（单条记录）

```yaml
- id: H-2026-11-14-001            # 必填，全局唯一（如 H-YYYY-MM-DD-NNN）
  title: "MACD 死叉离场优于 MA10 破位"
  rationale: "435 轮回测，MACD-only +2.41% vs 实际 +0.72%；属事后假设，必须走 OOS"
  pre_registered_at: "2026-11-14" # 必填，登记日（严格 YYYY-MM-DD）
  method:
    pairing: fifo                 # 必填：fifo | wave（口径声明）
    universe: "IR 系 435 轮"      # 必填：样本范围
    is_window: ["2024-09-24", "2025-12-31"]
    oos_window: ["2026-01-01", "2026-11-10"]
  pass_criteria:
    min_oos_improvement_pp: 2.0   # OOS 至少改善 2 个百分点
    max_mdd_increase_pp: 5.0      # 回撤最多恶化 5 个百分点
    require_significance: false   # 是否要求统计显著
  status: pending                 # pending | passed | failed | rejected
  evidence: null                  # passed 时必填（验证结果/出处）
  decided_at: null                # passed 时必填（YYYY-MM-DD）
```

**状态机**：`pending` →（验证后）`passed` / `failed` / `rejected`。
`passed` 强制要求 `evidence` 非空 + `decided_at` 合法日期——**不许自证**；
`pending` 阶段不得预填 evidence（`tests/test_hypothesis_registry_valid.py` 有断言）。

当前登记册预填 2 条（均为 `pending`）：

| id | 假设 | 口径 | IS | OOS |
|---|---|---|---|---|
| H-2026-11-14-001 | MACD 死叉离场优于 MA10 破位 | fifo | 2024-09-24 ~ 2025-12-31 | 2026-01-01 ~ 2026-11-10 |
| H-2026-11-14-002 | 分批止盈优于一次性清仓 | wave | 2024-09-23 ~ 2025-12-31 | 2026-01-01 ~ 2026-11-13 |

## 四、如何新增一条假设

### 步骤 1：先确定"要验证什么"

- 一句话写清假设（可证伪）；
- 确定口径（`fifo` / `wave`）、样本范围、IS/OOS 窗口、通过标准；
- 注意：**看到结果之后才想到的规则，仍可登记，但 rationale 必须写明"事后"**，
  并且必须走 OOS——事后假设不是不能验，是不能当已经验过。

### 步骤 2：写入登记册（推荐代码追加）

```powershell
# 在项目根运行（Windows PowerShell）
.\.venv\Scripts\python.exe -c "from research.registry import append_entry; append_entry({'id':'H-2026-11-14-003','title':'示例假设','rationale':'先验理由（未看结果）','pre_registered_at':'2026-11-14','method':{'pairing':'fifo','universe':'IR 系 435 轮','is_window':['2024-09-24','2025-12-31'],'oos_window':['2026-01-01','2026-11-10']},'pass_criteria':{'min_oos_improvement_pp':2.0,'max_mdd_increase_pp':5.0,'require_significance':False},'status':'pending','evidence':None,'decided_at':None})"
```

也可以手工编辑 YAML 后跑校验（手改请保持字段名精确，未知字段会被判非法）：

```powershell
.\.venv\Scripts\python.exe scripts\check_hypotheses.py
# 合法 → 退出码 0 并打印中文摘要；非法 → 退出码 1 并逐条列出错误
```

`append_entry` 的纪律：**校验失败 raise ValueError，且原文件一个字节都不改**。

### 步骤 3：跑验证（IS 定参 → OOS 验证）

```python
from lihu_quantify.backtest.split import split_by_date, compare_oos

is_rows, oos_rows = split_by_date(trades, "date",
                                  ["2024-09-24", "2025-12-31"],
                                  ["2026-01-01", "2026-11-10"])
# ...分别算 IS / OOS 指标（口径写进报告）...
result = compare_oos(is_metric, oos_metric, min_improvement_pp=2.0)
assert result["passed"] is (oos_result_is_good)   # 以 OOS 为准
```

### 步骤 4：回填结果

- 通过：`status: passed`，`evidence` 写清验证结果/脚本/显著性，`decided_at` 写验证日；
- 未通过：`status: failed`，evidence 写清"OOS 未达门槛"，**不得改 OOS 窗口重试**；
- 不可检验/前提被推翻：`status: rejected`，写清原因。

### 步骤 5：再跑一次校验

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_hypothesis_registry_valid.py -q
.\.venv\Scripts\python.exe scripts\check_hypotheses.py
```

`tests/test_hypothesis_registry_valid.py` 已接入全量 pytest：**登记册写坏 → 全量测试红**，
不需要新的 CI 配置。

## 五、上线闸门

> **未登记的参数变更不得上线。**

- 代码改动若涉及策略参数、离场规则、闸门阈值、仓位上限等**会影响交易决策**的内容，
  必须先有登记册条目，且 `status: passed` + evidence 可追溯；
- `status: pending` 的假设可以在研究脚本里验证，**不得进入生产配置**；
- 登记册只约束"研究结论 → 生产"这一步，不替代代码评审与测试；
- 本闸是**流程闸**，不是运行时拦截：`scripts/check_hypotheses.py` 只读校验，
  不执行回测、不写任何文件、不改变交易行为。

## 六、已知局限（诚实边界）

1. **本闸防不住前视偏差本身**：`lag` 只能由回测引擎保证（见案例 1），登记册只能
   防止"事后挑规则"和"全样本调参"；任何 OOS 数字仍要单独核对数据对齐。
2. **样本量小**：IR 系合并样本仅数百轮，OOS 段更短；`require_significance: true`
   在 Power 不足时可能永远无法通过——这本身是重要信息（应登记为 failed/rejected，
   而不是放宽标准）。
3. **口径中性化未自动化**：H-002（分批止盈）必须先做仓位/期限中性化再比较，
   本工具不自动做，需在验证脚本里手工处理。
4. **没有 git hook / 服务端强制**：目前靠 pytest 全量运行触发校验；如果有人绕过
   pytest 直接改配置，流程闸拦不住——这是制度局限，需在代码评审中人工确认。
5. **登记册不自动重跑回测**：验证脚本与证据由研究者提供，本工具不验证证据真伪
   （只验证"有没有写"），最终仍需人对 evidence 负责。
